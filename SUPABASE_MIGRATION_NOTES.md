## What did *not* need to change

Lovable Cloud is managed Supabase, so the data layer was already Supabase-native.
A full sweep of the project found:

- **68 source files** use the shared `supabase` client from
  `@/integrations/supabase/client` — none construct their own client or hardcode
  a URL. Repointing `.env` repoints the whole app.
- **No Edge Functions** (`supabase/functions/` does not exist), no
  `supabase.functions.invoke()` calls anywhere.
- **No Storage buckets** — no `supabase.storage` usage.
- **No Realtime** — no `supabase.channel()` usage.
- **No Lovable AI / AI Gateway calls.**
- **9 migrations** in `supabase/migrations/` are plain Postgres + Supabase SQL
  with no Lovable-specific extensions, vault references or proprietary schemas.
- `src/integrations/supabase/types.ts` is generated from the schema and stays
  valid as long as the new project's schema matches the migrations.

## ⚠️ Security caveats (unchanged from before — flagged, not altered)

These were already true on Lovable Cloud. Nothing here was changed, because
changing it would break the app. Worth fixing before this goes anywhere public.

**1. Passwords are stored in plain text.**
`src/lib/auth.tsx` compares `data.password_hash !== password` directly against
the column value. The seeded admin row stores the literal password string.
Despite the column name, nothing is hashed.

**2. Every table is world-readable and world-writable.**
Migration `20251229162227_…sql` replaced all the role-scoped RLS policies with
`USING (true)` / `WITH CHECK (true)` so the custom login could work through the
anon key. Combined with (1), anyone who opens the app's JavaScript bundle can
read the publishable key and then:

```
GET https://lfxjrzsmhtgmhgjbhpxo.supabase.co/rest/v1/system_users?select=*
```

…which returns every username and password in the system. They can also write to
every business table.

**3. The publishable key is committed to the repo.**
That part is fine on its own — publishable keys are designed to be public. The
problem is only that the RLS policies behind it grant everything.

### The proper fix, when you're ready

Move the login to Supabase Auth (the `profiles` / `user_roles` / `has_role()`
scaffolding from the earlier migrations is already there and unused), then
restore role-scoped RLS policies. That removes the plaintext passwords and the
open-table problem in one pass.

A smaller interim step: hash passwords with `pgcrypto` and move login behind a
`SECURITY DEFINER` RPC, then revoke direct anon access to `system_users`. That
closes the worst hole (credential dump) without touching the other tables.
